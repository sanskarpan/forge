# Design: forge Phase 7f — Select→cmov Diamond Fusion

**Status:** Approved for planning
**Scope:** CHECKLIST.md Phase 7's bullet: *"`Select` → `cmov` (integer) or `vblendvpd` / `minsd`+`maxsd` idioms (float) — branchless where profitable"* — explicitly deferred from Phase 7b to a named Phase 7f (see `docs/superpowers/specs/2026-08-09-phase-7b-two-address-hints-lea-synthesis-design.md`'s "Why `Select`→`cmov` is deferred to Phase 7f" section). Lives in `crates/forge-x64` (`select()` and a new pre-pass, mirroring 7b's `find_fully_fusable_scaled_indices` architecture).
**Input:** `forge_ir::Function` (specifically `Terminator::Branch`/`Terminator::Jump`/`Inst::Phi` shapes), the already-built `Assembler::cmovcc` (`crates/forge-x64/src/assembler.rs`, golden-byte tested, Phase 6) and `MachineInst::FloatMin`/`FloatMax` (Phase 7a).
**Out of scope**: real byte emission (same deferred-to-task-#68 boundary as every other Phase 7/8 MachineInst), a real profitability *benchmark* (no encode-and-execute pipeline exists yet to measure against — see "Why this can't be benchmarked yet" below), and — the largest scope reduction this design makes — **fusion of diamonds whose arms contain any computation at all**. Only diamonds whose arm blocks are EMPTY (pure value selection between two already-live values) are fused. See "Why only empty-arm diamonds" below.

## Why there is no `Inst::Select` to match on

SPEC.md's original §4 sketch included `Select { cond: Value, then_: Value, else_: Value }` as a real IR node — never built. `forge_ir::Inst` (`crates/forge-ir/src/ir.rs`) has no `Select` variant at all; `if`/`else` lowers exclusively via `Terminator::Branch { cond, then_, else_ }` + two blocks + a `Phi { incoming: SmallVec<[(Block, Value); 2]> }` at the merge point, and this is the ONLY form a `then`/`else` conditional expression ever takes in this compiler, all the way from the front-end through every optimizer pass. So "Select→cmov" cannot be an incremental match-arm the way every other Phase 7 bullet was (7a's per-`Inst` dispatch, 7b's `lea`/hint work) — it means recognizing a **CFG shape** spanning 4 blocks (branch, then-arm, else-arm, merge) and rewriting it to avoid the two real jumps entirely. This is exactly what 7b's deferral note anticipated and is the reason this slice needs its own pre-pass, architecturally mirroring 7b's `find_fully_fusable_scaled_indices` (a whole-`Function` analysis run once before `Selector` construction, feeding a set/map into the `Selector`) but operating at block granularity instead of value granularity.

## Why only empty-arm diamonds

**The correctness hazard that makes "just always fuse" wrong**: converting a branch into unconditional execution of both arms is only safe if BOTH arms are side-effect-free *and* trap-free. This language has no I/O/memory operations (confirmed in Phase 7a's own research — no `Load`/`Store`, nothing to have a side effect on), so "side-effect-free" is free for any pure arithmetic. But it is NOT trap-free in general: `Inst::Div`/`Inst::Rem` on integer operands lower to `IntDiv`/`IntRem` (`cqo` + `idiv`), and x86's `idiv` is a REAL HARDWARE FAULT (SIGFPE) on division by zero or on `i64::MIN / -1` — not a soft, catchable condition. A program like `if b != 0 then a / b else 0` is currently, correctly, safe: the division only ever executes when the branch guarantees `b != 0`. Naively fusing this into "always compute `a/b`, then cmov the result away if unneeded" would make a previously-safe program crash on inputs it used to handle correctly — a severe, silent regression, exactly the kind of "looks like a pure optimization, is actually a correctness bug" trap this project's history has hit before in different forms (Phase 4's floating-point-trap table, Phase 8's whole point-in-time-vs-lifetime saga).

**The scope decision this design makes**: rather than building a full "is this instruction provably trap-free" classifier (a real, non-trivial analysis — `IntDiv`/`IntRem` are the only traps *today*, but a classifier would need to be exhaustive and kept exhaustive as new `Inst` variants are added, the same "no wildcard arm" discipline `select_inst`/`uses_of` already enforce elsewhere) and inlining arbitrary arm computation, this slice restricts fusion to diamonds whose arm blocks are **completely empty** — `BlockData::insts.is_empty()` for both `then_` and `else_`. An empty arm block can contain no `IntDiv`/`IntRem` (or anything else) by construction, so the entire trap-safety question is moot without needing any classifier at all. This is a real, deliberate, and large scope reduction, stated honestly: real corpus test cases like `"if a > b then (a * c) + (b * c) else a - b"` (both arms compute something) will NOT be fused by this slice — only the shape `if cond then x else y` where `x`/`y` are already-existing values (parameters, constants, or values computed *before* the branch) is eligible. This still covers a real, common pattern already present in this project's own test corpus verbatim: `"(if a > b then a else b) + a"`.

Extending to non-empty, provably-trap-free arms is a natural, well-scoped future slice once this one ships and a real trap classifier is designed on its own — not attempted here, matching this project's YAGNI discipline (Phase 8c/8d each explicitly deferred similar "the obviously bigger version of this feature" temptations for the same reason: build what's needed and provably correct now, not what's speculatively more general).

## The diamond shape recognized

```
   [pred: Branch { cond, then_: T, else_: E }]
        /                          \
   [T: BlockData::insts == []]   [E: BlockData::insts == []]
   [T: Terminator::Jump(M)]      [E: Terminator::Jump(M)]
        \                          /
         [M: starts with Phi { incoming: [(T, valT), (E, valE)] }]
```

Exact eligibility, checked by a new pre-pass (see below):
1. `pred`'s terminator is `Branch { cond, then_: t, else_: e }` with `t != e` (a degenerate `Branch{then_==else_}` is already handled by `successors_of`-style deduping elsewhere and isn't a real diamond).
2. `func.blocks[t].insts.is_empty()` and `func.blocks[e].insts.is_empty()`.
3. `func.blocks[t].term` is `Jump(m)` and `func.blocks[e].term` is `Jump(m)` for the SAME block `m`.
4. `m`'s only predecessors are `t` and `e` (checked via `BlockData::preds`, or re-derived the way `forge-regalloc`'s `intervals.rs` already does elsewhere in this project rather than trusted, since `preds` is `Builder`'s own bookkeeping and can be stale on a hand-built `Function` — see the "why re-derive predecessors" precedent already established in `forge-regalloc/src/intervals.rs`'s critical-edge check).
5. **Corrected after execution-based review found the earlier draft's "exactly one Phi at `m`" claim is false on real, ordinary source text.** `m` can contain MULTIPLE `Inst::Phi`s — SSA construction mints one for every variable still live across the join, not just the `if`/`else` expression's own result. Confirmed by execution: `"(if a > b then a else b) + a"` (this design's own cited example) produces TWO phis at the merge block — the diamond's real payload (`incoming: [(t, valT), (e, valE)]`, genuinely differing) AND a second, trivial phi for `a` (`incoming: [(t, a), (e, a)]`, identical on both edges, since `a` is live across the join but untouched by either arm); a longer example (`"c + (if a > b then a else b) + a + b"`) produces three. The corrected rule: find the UNIQUE phi at `m` whose two incoming values DIFFER (`incoming[0].1 != incoming[1].1`) — that is the diamond's payload, and it need not be `m`'s first instruction. Every OTHER phi at `m` must be trivial (both incoming values identical) — if any other phi at `m` also has differing incoming values, `m` is not eligible for fusion (more than one thing genuinely differs between the arms, which this design's single-value fusion can't represent). A trivial phi's `dst` still needs a real value after fusion (it can't be silently dropped, since real code may reference it) — it is resolved exactly as it already would be without fusion, no different: `def_of`/interval-building treats it as any other phi with identical incoming edges, unaffected by whether `t`/`e` still exist as separately-selected blocks.
6. `valT`/`valE`'s `Ty` matches (guaranteed by typeck — both arms of one `if`/`else` expression always have one unified type).

## The float min/max special case

`if a < b then a else b` (and `then b else a`, and `>`/`>=`/`<=` variants) is a special case of the empty-arm shape above where `valT`/`valE` are exactly the two operands of the branch's own condition, `cond = Cmp(op, a, b)`. This is recognized as a SEPARATE, narrower pattern within the same pre-pass and rewritten to the ALREADY-BUILT `MachineInst::FloatMin`/`FloatMax` (Phase 7a, real `minsd`/`maxsd` encoder support already shipped, Phase 6) instead of a `cmov`-family instruction — directly satisfying CHECKLIST bullet 244's literal "`minsd`+`maxsd` idioms (float)" wording with ZERO new encoder work. `Inst::Min`/`Inst::Max` (the `min()`/`max()` builtin intrinsics, `forge-ir/src/lower.rs`) are a SEPARATE, pre-existing lowering path — this pattern only fires for a RAW `if`/`else` shaped exactly like a min/max comparison, which is a real, additional case the builtin doesn't cover (a user writing `if a < b then a else b` by hand gets the same optimized code as one calling `min(a, b)`).

**The exact op/arm-selection table — CORRECTED after execution-based review found rows 2 and 4 of an earlier draft produce a real, source-reachable miscompile.** Real x86 semantics: `MINSD dst,src` computes `dst = (dst < src) ? dst : src`, `MAXSD dst,src` computes `dst = (dst > src) ? dst : src`, where by this project's own `dst`-reuses-`lhs` coalescing convention `dst`/`lhs` is hardware SRC1 and `rhs` is hardware SRC2 — and CRITICALLY, on an UNORDERED-OR-EQUAL comparison (NaN in either operand, or `+0.0` vs `-0.0`, which compare equal but are bit-distinct), the hardware result is **always SRC2** (`rhs`), never SRC1. This means the invariant that actually determines correctness is **"the diamond's `else`-arm value must be `rhs`,"** not "which comparison operator was used" — an earlier draft's table got this backwards for two of the four rows and its own stated justification ("restricting to strict `<`/`>` sidesteps the tie question") was false on its face, since a STRICT comparison still has a tie case (`a < b` is exactly false when `a == b`, routing execution to the else-arm, which is exactly where the earlier draft's rows 2/4 diverged). Confirmed by execution: `"(if a < b then b else a) + a"` (an entirely ordinary way to spell `max`) with `a=+0.0, b=-0.0` — real source semantics (Rust `<`, IEEE default, matching `forge-ir/src/interp.rs`'s reference interpreter) yield `+0.0`; the earlier draft's table yielded `-0.0`.

| `cond`'s `CmpOp` | `valT` (then-arm) | `valE` (else-arm) | Rewrite |
|---|---|---|---|
| `Lt` (`a < b`) | `a` | `b` | `FloatMin { dst, lhs: a, rhs: b }` |
| `Lt` (`a < b`) | `b` | `a` | `FloatMax { dst, lhs: b, rhs: a }` |
| `Gt` (`a > b`) | `a` | `b` | `FloatMax { dst, lhs: a, rhs: b }` |
| `Gt` (`a > b`) | `b` | `a` | `FloatMin { dst, lhs: b, rhs: a }` |

(Rows 1 and 3 are unchanged from the earlier draft and were always correct — confirmed by execution across ±0/NaN/ordinary inputs. Only rows 2 and 4's operand order changes: the else-arm value is always `rhs`, the then-arm value is always `lhs`, regardless of which of `a`/`b` that happens to be.)

`Le`/`Ge` are EXCLUDED from this table — not because strict comparison "sidesteps" the tie question (it doesn't; every row above already handles ties correctly via the lhs/rhs=then/else invariant), but because `Le`/`Ge`'s OWN tie case sends execution to a DIFFERENT arm than `Lt`/`Gt`'s does for the same operand pair, which is a real, separate semantic difference this design has not derived a table for. `Le`/`Ge`-shaped diamonds are NOT matched by this table and MUST NOT fall through to the general integer cmov path either (that path is GPR-only — see the corrected eligibility rules below); they are simply left unfused, keeping their real `Branch`+`Phi` lowering, which is always correct, just not branchless. A future slice could derive the `Le`/`Ge` table properly; this one does not attempt it.

Diamonds matching the empty-arm shape but NOT this min/max table, and that are INTEGER-typed, fall through to the general cmov path below. **This does NOT include float third-value diamonds** (e.g. `if a < b then a else c` for some unrelated third value `c`, still `F64`-typed) — those are excluded outright, same as `Le`/`Ge`, by the hard `Ty::I64`/`Ty::Bool`-only gate the general cmov path enforces (see below); they produce no fusion at all, never an `IntCmov`.

## The general cmov path (integer only — a HARD type gate, not a fallback)

**Correction after execution-based review found a second real, source-reachable miscompile**: an earlier draft of this section described `Le`/`Ge`-shaped and third-value float diamonds as "falling through" from the min/max table to this general path. That is wrong and dangerous — this path constructs `MachineInst::IntCmov`, which the encoder can only ever realize as a GPR `cmovcc` (there is no XMM `cmov` on x86-64), and `Le`/`Ge`/third-value float diamonds have `valT`/`valE` typed `F64`/`RegClass::Xmm`. Confirmed by execution: implementing the "fall through" wording literally, `"if a >= b then a else b"` and `"if a > b then a else c"` (this design's own example of a third-value diamond) both produce `IntCmov { dst: Xmm-class, cond: Xmm-class-derived-bool, then_val: Xmm-class, else_val: Xmm-class }` — an `IntCmov` over XMM-classed values, which `build_intervals`/`allocate`/`verify_allocation` all silently accept as `Ok(())`, so the miscompile is invisible until task #68 tries to encode a `cmovcc` on registers `Assembler::cmovcc` was never meant to receive. **The fix: this path requires a HARD, checked precondition, enforced in `find_fusable_diamonds` itself, not left to prose.** `find_fusable_diamonds` lives in `crates/forge-x64` and `crates/forge-x64` does NOT depend on `crates/forge-regalloc` (dependencies run the other way — `forge-regalloc` depends on `forge-x64` — a clean, one-directional layering this design must not break just to reuse a name), so the check cannot literally be `RegClass::of(ty_of(dst)) == RegClass::Gpr` — `RegClass` is not a type `forge-x64` can name. The equivalent, LOCALLY-available check uses `forge_ir::Ty` directly, which `forge-x64` already imports everywhere: `ty_of(dst) != Ty::F64` (`forge_ir::Ty` has exactly three variants — `F64`, `I64`, `Bool` — and `F64` is the only one XMM-classed anywhere in this codebase, `RegClass::of`'s own real implementation in `forge-regalloc` is built from precisely this same distinction, so this is not a parallel, potentially-drifting reimplementation, just the one underlying fact `forge-x64` is actually allowed to reference). Any empty-arm diamond that is neither a min/max-table match NOR `Ty::I64`/`Ty::Bool`-typed is classified as UNFUSABLE and left on its real `Branch`+`Phi` path; there is no third option and no fallback between the two fusion kinds.

For an empty-arm diamond that ISN'T the float min/max shape, and where `valT`/`valE` are confirmed `Ty::I64`/`Ty::Bool`-typed (i.e. NOT `Ty::F64` — GPR-equivalent in `RegClass::of`'s own terms, checked locally via `Ty` since `forge-x64` cannot name `RegClass` itself) — checked, not assumed: a new MachineInst variant,

```rust
/// Branchless select: dst = (cond != 0) ? then_val : else_val. Produced
/// ONLY by diamond fusion (crates/forge-x64/src/machine_inst/diamond.rs)
/// -- select_inst never constructs this directly, since there is no
/// Inst::Select to match on (see this file's design doc). 2-address
/// destructive like every other x86 binary op: dst starts as a copy of
/// then_val (a coalescing hint records dst -> then_val, same convention
/// as IntAdd/etc.), and emission (deferred, task #68) overwrites it with
/// else_val conditionally via `test cond, cond` (reads cond's already-
/// materialized 0/1 value directly, NOT the flags from whatever produced
/// it -- those are long clobbered by the time a real diamond's arms, if
/// any existed, would have run; using a fresh test right before the cmov
/// is correct regardless of cond's origin) followed by `cmovz dst,
/// else_val` (CMOVZ: if ZF=1, i.e. cond's materialized value was exactly
/// zero/false, overwrite dst with else_val -- else dst keeps then_val).
IntCmov {
    dst: Value,
    cond: Value,
    then_val: Value,
    else_val: Value,
},
```

**Why `test`+`cmovz` and not a flags-reuse of the original comparison**: the diamond's `cond` was very likely produced by an `IntCmp`/`FloatCmp` earlier in the instruction stream (materializing a real 0/1 `Bool` via `cmp`/`ucomisd`+`setcc`, Phase 7a), but by the time execution reaches where the fused `cmov` goes (logically, where the merge block used to be), ANY number of intervening instructions may have run and clobbered EFLAGS — flags are not preserved across arbitrary instructions the way a register-resident value is. The only thing safe to rely on is `cond`'s already-materialized 0/1 VALUE, sitting in whatever register/slot the allocator gives it, which `test cond, cond` re-derives fresh flags from, immediately before the `cmovz` that consumes them. This works regardless of what `Inst` actually produced `cond` (a direct `Cmp`, a `Not`/`And`/`Or` combination, or even a `ConstBool` — no special-casing needed), because it never depends on that instruction's own flags surviving. Confirmed by execution: `Assembler::test_reg_reg` (`REX.W + 85 /r`) exists and is exactly this primitive; `cmovcc(ConditionCode::Equal, ...)` reaches `cmovz`'s `0F 44` encoding.

**A real precondition this design depends on but does not itself establish**: `Assembler::test_reg_reg` is `REX.W`-prefixed — it tests all 64 bits of the register. `Assembler::setcc`'s own doc comment already states it "writes ONLY one byte — the upper bits of `dst` are left as whatever was there before; producing a clean full-width 0/1 is instruction-selection's job," and nothing in this codebase currently zero-extends a `setcc` result (`movzx` is unused anywhere today). If `cond`'s upper 56 bits are garbage rather than zero, `test cond, cond` can set `ZF=0` for a logically-false `cond`, and the fused `cmovz` picks the wrong arm — silently, since nothing here would catch it. This is NOT a new problem this design introduces (any future full-width use of a `setcc`-materialized `Bool` would hit the same issue). **Scope decision, stated explicitly to resolve a tension an earlier draft left unaddressed**: this design produces only the `MachineInst`-level SELECTION representation, the same boundary every other MachineInst in this codebase already respects — it emits no real bytes and cannot itself fix an encoder-level zero-extension gap in how `setcc` materializes a `Bool`. Guaranteeing `cond` is genuinely zero-extended before `test cond, cond` runs is real byte-emission-time work and is task #68's responsibility, not this slice's — recorded here as a load-bearing precondition task #68 must satisfy (e.g. via a `movzx` after `setcc`, or a guaranteed-zeroed destination register before the `setcc` byte-write) before this design's `IntCmov` sequence can be correctly emitted, not something this slice adds a test or exit criterion for.

Both fusion cases (min/max float rewrite, general integer cmov) leave the merge block's `Phi` instruction with NOTHING left to do — the fused instruction writes directly into the Phi's own destination `Value` (`dst` above IS the Phi's `dst`), so when `select_inst`'s existing, unmodified `Inst::Phi => { /* emits nothing */ }` arm is reached during the normal per-block walk over `m`, it is *already* correctly a no-op for this specific `Value` — no change needed to that arm at all. What DOES need a code change: the pre-pass must prevent `t` and `e` from being walked at all (both are empty, so this is a true no-op skip, not real suppression of computed values the way 7b's lea-fusion suppression works), and `m` itself is walked normally except the diamond's own `Phi` is already covered by the fused instruction emitted at `pred`'s position.

## Where this hooks into `select()`

Following 7b's exact template (`find_fully_fusable_scaled_indices`, called once at the top of `select()`, before `Selector` construction):

```rust
/// Detects every diamond eligible for fusion (see design doc). Returns a
/// map from the diamond's BRANCH block to the fusion decision -- either a
/// float min/max rewrite or a general integer cmov -- keyed for lookup
/// when select()'s RPO walk reaches that block's terminator. Also
/// returns the set of arm blocks (t, e) to skip entirely during the walk
/// (always empty per-instruction, by construction of eligibility, so
/// "skip" here never discards real computed values -- unlike 7b's
/// suppression of dead lea-fused Mul/Shl, which does).
fn find_fusable_diamonds(func: &Function) -> (HashMap<Block, DiamondFusion>, HashSet<Block>) {
    // for each block with a Branch terminator: check eligibility (shape
    // above), classify float-min-max vs. general-int, record.
}

enum DiamondFusion {
    FloatMinMax { dst: Value, op: MinMaxOp, lhs: Value, rhs: Value }, // op: Min | Max
    IntCmov { dst: Value, cond: Value, then_val: Value, else_val: Value },
}
```

`select()`'s RPO loop (`crates/forge-x64/src/machine_inst/mod.rs`, currently walking every block unconditionally) gains: (1) skip any block in the arm-block-skip set entirely (no per-`Value` walk, no terminator lowering — it contributes NOTHING to `insts`, same "two adjacent `block_starts` entries share one start" shape `SelectedFunction::block_starts`'s own doc comment already anticipates for exactly this reason) — **a skipped block still gets its own `block_starts` entry pushed** (a zero-length range sharing its start position with the next real entry), exactly like any other zero-`MachineInst`-contributing block already does (confirmed by execution: the existing positional-lookup contract handles this correctly with no special-casing, as long as the entry itself is never omitted); (2) when `select_term` is about to lower a `Branch` terminator whose block is a fusion key, emit the `FloatMin`/`FloatMax`/`IntCmov` MachineInst instead of `MachineInst::Branch`, and do NOT also emit a `Jump` (the fused instruction falls through directly to `m`, which is walked immediately next in RPO order since `m` is `pred`'s sole real remaining successor once `t`/`e` are elided) — **guarded by a `debug_assert!` at the fusion point that the next block RPO actually visits after `pred` is indeed `m`**, rather than silently trusting this. Confirmed true by execution across 11 real programs including doubly-nested diamonds, but it is a property of this front-end's structured CFG generation, not something the fusion logic itself enforces — a `debug_assert!` turns a silent wrong-fall-through (running into whatever block RPO happens to visit next, with no `Jump` to redirect it) into a loud, caught failure if that property is ever violated by a future front-end/optimizer change, rather than a silent miscompile.

**Two more corrections from execution-based review, both real but non-miscompiling (documentation/completeness gaps, not correctness bugs):**

- **`compute_coalescing_hints`** (`machine_inst/mod.rs`) ends in a wildcard `_ => {}` arm, so it compiles fine against a new `IntCmov` variant but silently produces NO hint for it — directly contradicting this doc's own `IntCmov` doc comment claim ("a coalescing hint records `dst -> then_val`, same convention as `IntAdd`/etc."). Confirmed by execution: without an explicit `IntCmov` arm added to `compute_coalescing_hints`, the fused int diamond gets zero `dst -> then_val` hint, unlike the float min/max path (which gets one for free, since `FloatMin`/`FloatMax` are already listed there from Phase 7a). This is a real, silent gap the Rust compiler will not catch (unlike `reads_of`/`def_of`'s exhaustive matches) — `compute_coalescing_hints` must gain an explicit `IntCmov` arm, and this is now a named exit criterion below, not left implicit.
- The `FloatCmp` that produces `cond` for a fused min/max diamond becomes dead after fusion (the fused `FloatMin`/`FloatMax` never reads it) but is still emitted, since this design has no dead-instruction-suppression mechanism for the fusion path the way 7b's lea fusion suppresses now-dead standalone `Mul`/`Shl` computations. This weakens the "profitable is not really in question" argument slightly (the fused sequence still pays for the now-unnecessary `ucomisd`+`setcc`) — recorded honestly as a real, known inefficiency in this slice rather than silently ignored; suppressing it would follow 7b's exact precedent and is a reasonable, well-scoped follow-up, not attempted here to keep this slice's own scope from growing.
- Fusion operates ENTIRELY on the `MachineInst` output of `select()` — it never mutates the input `forge_ir::Function`. Confirmed by execution: `forge-regalloc`'s `merge_phi_intervals` critical-edge tripwire (which runs on the unmodified IR `Function`) sees the diamond's ORIGINAL, un-fused shape regardless of whether `select()` fuses it, and the whole 8a-8e corpus run through fused `select()` output triggers zero tripwire panics. `successors_of`'s own doc comment (`forge-regalloc/src/intervals.rs`) anticipating that "Phase 7f's diamond fusion plausibly could" synthesize a degenerate `Branch{then_==else_}` does not apply to this design specifically, since it never touches `Terminator` shape at the IR level — worth a one-line note there once this slice ships, so a future reader doesn't go looking for an interaction that was never built this way.

## Why this can't be benchmarked yet, and what "profitable" means for now

CHECKLIST's bullet says "branchless where profitable" — this project's own established discipline (`docs/superpowers/specs/2026-08-09-phase-7b-two-address-hints-lea-synthesis-design.md`'s deferral reasoning, verbatim) is that profitability should be MEASURED, not assumed, and there is still no encode-and-execute pipeline anywhere in this codebase to measure against (`crates/forge-x64/src/assembler.rs` has zero `MachineInst` references; task #68, "Final code-emission pipeline," remains not started). Building a throwaway measurement harness scoped to just this feature, ahead of the real pipeline, would be exactly the kind of speculative, parallel-track infrastructure this project has consistently avoided building early (e.g. Phase 7e explicitly declined to build a one-off call-sequence emitter ahead of task #68).

**What this design does instead**: restrict fusion to the empty-arm shape specifically BECAUSE it's the one case where "branchless is profitable" is not really in question at a micro-architectural level — avoiding a branch entirely (no possible misprediction penalty at all, since there's nothing to inline or unconditionally compute beyond one `test`+`cmovz` or one `minsd`/`maxsd`, both single, fast, well-pipelined instructions) versus two real conditional jumps plus whatever copy the `Phi` would otherwise need is close to strictly better on virtually all modern x86-64 microarchitectures for this exact narrow shape, which is precisely why classic compiler folklore treats "ternary of two live values" as the textbook safe-to-always-fuse case and reserves real cost-model heuristics for the "arms contain computation" case this design explicitly excludes. Once task #68 exists and real programs can be compiled, mmap'd, and timed, an actual before/after measurement (mirroring `forge-regalloc/benches/allocation.rs`'s criterion setup, the one benchmark precedent in this workspace) becomes a natural, separately-scoped follow-up to confirm this reasoning empirically rather than resting on it by assertion alone — recorded honestly as future work, not built speculatively now.

## Testing

- `find_fusable_diamonds`: a hand-built `Function` with the exact eligible shape (empty arms, a differing-incoming payload phi at `m`, sole predecessors) → detected, correctly classified as `IntCmov`. A near-miss with a NON-empty arm block → NOT detected (stays on the real `Branch`+`Phi` path) — the test that would fail if the "empty arms only" restriction were accidentally dropped. A near-miss where `m` has an extra predecessor beyond `t`/`e` → NOT detected. A near-miss where `t`'s/`e`'s terminator jumps somewhere OTHER than a shared block → NOT detected. **A `m` with MULTIPLE phis, exactly one of which genuinely differs (the corrected rule 5 shape)** → the payload phi correctly identified regardless of its position among `m`'s instructions, the trivial phi(s) left untouched and unaffected. **A `m` with two DIFFERING phis** → NOT detected (more than one thing differs between the arms; this design's single-value fusion doesn't apply).
- Float min/max table: all 4 CORRECTED rows (`Lt`/`a,b` → `Min{lhs:a,rhs:b}`, `Lt`/`b,a` → `Max{lhs:b,rhs:a}`, `Gt`/`a,b` → `Max{lhs:a,rhs:b}`, `Gt`/`b,a` → `Min{lhs:b,rhs:a}`) each get a dedicated hand-built test confirming the exact `FloatMin`/`FloatMax` + operand order produced, PLUS an explicit ±0.0 and NaN input test per row confirming the fused form's result bit-for-bit matches `forge-ir/src/interp.rs`'s reference interpreter's real semantics (not just "some plausible value") — this is the test that would have caught the miscompile execution-based review found in an earlier draft of this design, and must not be weakened to a same-value-class check. `Le`/`Ge`-shaped diamonds AND float third-value diamonds (e.g. `if a > b then a else c`) → confirmed to produce ZERO fusion at all (neither `FloatMinMax` NOR `IntCmov` — this is the test that would catch the earlier draft's "fall through to the general integer path" defect, which produced a real `IntCmov` over XMM-classed values).
- General `IntCmov`: a hand-built diamond selecting between two live `I64` values → `IntCmov` with the right `dst`/`cond`/`then_val`/`else_val`, and confirm the arm blocks contribute NOTHING to `SelectedFunction::insts` (both before AND after the fused instruction). A dedicated `Ty::I64`/`Ty::Bool`-only gate test: hand-build the SAME empty-arm shape but with `F64`-typed, non-min/max-pattern `valT`/`valE` → confirm `find_fusable_diamonds` classifies it as unfusable, not as `IntCmov`. `compute_coalescing_hints` produces a real `dst -> then_val` hint for a fused `IntCmov` (the silent gap execution-based review found — must be tested explicitly, since the compiler won't catch its absence).
- `SelectedFunction::block_starts`' positional contract under fusion, including that a skipped arm block still gets its own (zero-length) `block_starts` entry: confirm block boundary bookkeeping stays internally consistent for the corpus example `"(if a > b then a else b) + a"` specifically (the exact real string already used throughout this project's test corpus, and — confirmed by execution-based review — the ONE corpus string, along with `"if a > b then (if a > c then a else c) else b"`, that actually contains a fusable diamond; no corpus program exercises the `IntCmov` path, which needs its own hand-built I64 test, not a corpus-derived one) — re-run through `build_intervals`/`allocate`/`verify_allocation` (Phase 8's already-shipped, independent verifier) end-to-end, confirming a genuinely fused program still produces a VALID allocation, not just a plausible-looking `MachineInst` stream. This is one of the most valuable tests in this slice: it exercises the fused output against every downstream consumer this project has already built and independently verified, rather than trusting the new code's own unit tests alone.
- Re-run the ENTIRE existing 8a-8e corpus (`test_corpus()`, duplicated across `intervals.rs`/`linear_scan.rs`/`verify.rs`/`pressure.rs`) through `select()` with fusion enabled, confirming `verify_allocation` still returns `Ok` on every program — a corpus-wide regression guard that fusion never produces an unallocatable or unsound `MachineInst` stream, run the same way Phase 8's own corpus tests already are.
- A hand-built `IntDiv`/`IntRem`-in-arm near-miss, confirming it is NOT fused (would be a genuine hardware-trap-introducing bug if this test ever failed) — this is the single correctness-critical test in the whole slice and must not be treated as optional/lower-priority relative to the fusion-positive tests.

## Exit criteria

1. `find_fusable_diamonds(func: &Function) -> (HashMap<Block, DiamondFusion>, HashSet<Block>)` exists in `crates/forge-x64`, matches the CORRECTED eligibility rules above exactly (empty arms, shared single Jump target, sole predecessors, the unique-differing-phi rule — NOT "single Phi," which is false of real source text), and is called once at the top of `select()`, before `Selector` construction — mirroring 7b's `find_fully_fusable_scaled_indices` architecture precisely.
2. `MachineInst::IntCmov { dst, cond, then_val, else_val }` exists, is exhaustively handled everywhere `MachineInst` is already matched without a wildcard (`select_inst`'s own callers aside — this variant is never constructed by `select_inst` itself, only by the fusion path — but `reads_of`/`def_of` in `forge-regalloc/src/liveness.rs`, and any other exhaustive `MachineInst` match in the codebase, MUST gain an explicit arm or fail to compile, per this project's established "no wildcard arm" discipline) — **AND `compute_coalescing_hints` (`machine_inst/mod.rs`), which does NOT fail to compile without an update (it wildcards), must explicitly gain an `IntCmov -> dst,then_val` hint arm, verified by a dedicated test, not left as a silent gap.**
3. Float min/max diamonds (the CORRECTED 4-row table, strict `<`/`>` only, else-arm-is-always-`rhs`) rewrite to the EXISTING `MachineInst::FloatMin`/`FloatMax` — zero new encoder work for this half of the bullet. `Le`/`Ge` and float third-value diamonds produce NO fusion at all.
4. **`find_fusable_diamonds` enforces `ty_of(dst) != Ty::F64` (i.e. `Ty::I64`/`Ty::Bool` only — the locally-computable equivalent of `RegClass::Gpr`, since `forge-x64` cannot name `forge-regalloc`'s `RegClass` type at all without an illegal reverse dependency) as a hard, checked precondition on the `IntCmov` classification** — never a "fall through" from the float table, which was a real, source-reachable miscompile in an earlier draft (an `IntCmov` over XMM-classed values, silently accepted by `verify_allocation` since it has no type-mismatch check of its own — see `verify_allocation`'s own documented, deliberate scope boundary from Phase 8d).
5. `select()`'s RPO walk correctly skips both arm blocks of every fused diamond entirely (each still gets its own zero-length `block_starts` entry), does not double-emit a `Jump` alongside the fused instruction, and asserts (via `debug_assert!`) that the next RPO-visited block is genuinely `m`.
6. `SelectedFunction::block_starts`'s positional contract holds for fused output (verified by the dedicated test above, not just assumed from the doc comment already anticipating this shape).
7. The `IntDiv`/`IntRem`-in-arm (and any other non-empty-arm) near-miss is NEVER fused — the single correctness-critical exit criterion, tested explicitly, not merely implied by "empty arms only" being stated in prose.
8. The full 8a-8e corpus, run through `select()` with fusion enabled, still passes `verify_allocation` on every program.
9. `cargo test --workspace` green, `cargo clippy --workspace -- -D warnings` and `cargo fmt --check` clean.

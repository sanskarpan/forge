# Design: forge Phase 8 — Register Allocation, Sub-Slice Decomposition

**Status:** Approved for planning
**Scope:** How CHECKLIST.md's Phase 8 (24 tasks, "Register Allocation") splits into independently designable/implementable/reviewable sub-slices, following the same pattern Phase 6 (6a-6f) and Phase 7 (7a-7e, plus deferred 7f and a deferred final-emission task) already used successfully in this project. This doc does the splitting and states each slice's scope/exit-boundary; each slice gets its own design doc + plan + subagent-reviewed implementation afterward, exactly like every prior sub-slice.

## Where this lives, and what it receives

The allocator itself belongs in `crates/forge-regalloc` (currently a pure stub — empty `Cargo.toml`, one-line `lib.rs`), per PROMPT.md's and SPEC.md's own file paths (`crates/forge-regalloc/src/linear_scan.rs`) and SPEC.md's repo-layout description ("live intervals, linear scan, spilling, ABI constraints"). It will need `forge-ir` (for `Value`/`Ty`/`dominance::reverse_postorder`) and `forge-x64` (for `MachineInst`/`SelectedFunction`/`PhysReg`) added as real dependencies.

Phase 8's input is Phase 7's fully-built `SelectedFunction { insts: Vec<MachineInst>, synthetic_types: HashMap<Value,Ty>, coalescing_hints: HashMap<Value,Value>, pool: ConstantPool }`. Its output, once complete, is a per-`Value` `Location` (real `PhysReg` or spill slot) that the deferred "final code-emission pipeline" task will consume to produce real bytes. Phase 8 does NOT emit any bytes itself — same discipline as every Phase 7 sub-slice (build the real data/algorithm, defer byte emission).

**What Phase 8 receives already built, for free**: `forge_ir::dominance::reverse_postorder` (RPO block ordering) and `compute_dominators` (dominator tree, Cooper/Harvey/Kennedy). `SelectedFunction::coalescing_hints`, already fully computed by Phase 7b — Phase 8 only *consumes* this map (for two-address hints; hints from φ operands are new, since `Phi` selection was itself deferred to Phase 8 — see CHECKLIST.md:239's Phase 7a note). `prologue::SYSV_CALLEE_SAVED` and `padded_spill_bytes`/`emit_prologue`/`emit_epilogue`'s `spill_bytes: u32` parameter, already built and waiting for real input (Phase 7d).

**What Phase 8 must build from scratch**: `RegClass` (Gpr/Xmm — doesn't exist anywhere yet), ABI caller-saved/argument-register constant lists in actual code (SPEC.md has these as prose/pseudocode only), backward `live_in`/`live_out` dataflow (zero precedent in the codebase — `forge-opt`'s DCE-pass `live_insts` locals are a different, unrelated liveness concept), `Interval` construction, the linear-scan algorithm itself, the spill heuristic, spill-slot allocation with reuse (zero precedent anywhere), and an independent verifier.

## Sub-slice breakdown

**8a — Liveness, Intervals & ABI Foundations** (CHECKLIST bullets 1-5: linearize in RPO, backward liveness dataflow, `Interval` struct, loop-back-edge extension, φ-interval handling)
Builds the analysis layer everything else depends on: instruction numbering, `live_in`/`live_out` per block, and `Interval { value, start, end, reg_class, hint, fixed, spill_weight }` construction from the liveness result. Also where `RegClass` and the ABI register-class constants (which values are `Gpr` vs `Xmm`, which `MachineInst`s force a `fixed: Option<PhysReg>` — `Param`'s ABI argument position, `IntDiv`/`IntRem`'s implicit rax/rdx) get defined, since `Interval` itself carries `reg_class`/`fixed` fields and can't be built without them. Output: `fn build_intervals(selected: &SelectedFunction) -> Vec<Interval>`, no allocation happening yet. This is the highest-information-density, everything-downstream-depends-on-it slice — analogous to 7a's role in Phase 7.

**8b — Linear Scan Core** (CHECKLIST bullets 6-10, 15-16: sort by start, `active` sorted by end, `expire_old_intervals`, `pick_register` with hint preference, fixed-register eviction, coalescing hints wired into `pick_register`, separate GPR/XMM class allocation)
The allocator's main loop, following PROMPT.md's `LinearScan::run` sketch closely (Poletto & Sarkar with Mössenböck & Pfeiffer SSA refinements). No spilling logic yet — this slice assumes registers are always available (spilling is 8c) and focuses purely on the assignment loop's correctness: the `active`-sorted-by-end invariant, hint-then-free register selection honoring `coalescing_hints`, and fixed-register eviction for ABI/idiv constraints. GPR and XMM classes are allocated independently (two class-scoped runs, or one class-parameterized run — a real design decision for 8b's design doc, not decided here). This is likely the highest-risk slice, analogous to 7b's role — the interacting fixed-register-eviction + hint-preference + dual-class logic has real room for the kind of subtle ordering bug 7b's suppression pre-pass had.

**8c — Spilling** (CHECKLIST bullets 11-14: `spill_at_interval` victim selection, the furthest-endpoint-weighted-by-use-density heuristic, spill slot allocation with reuse, reload-before-use/store-after-def insertion)
What happens when 8b's `pick_register` fails to find a free register. Builds the actual spill-slot free-list/reuse mechanism (stack-frame-layout analogue of register allocation itself — needs its own expiry logic parallel to but distinct from `active`'s). This is also where `prologue.rs`'s `spill_bytes: u32` parameter finally gets a real value fed into it for the first time.

**8d — Verification & Reporting** (CHECKLIST bullets 17-18: independent allocation verifier, register-pressure-per-program-point reporting)
The verifier is explicitly required to be written without referencing the allocator's internals ("so it cannot share a bug with it" — PROMPT.md's own words), so it's naturally a separable, independently-reviewable unit — this project's established "written separately, can't share a bug" pattern (mirroring 7b's fusion-decision/suppression-decision sharing ONE function specifically so they COULD NOT disagree; here the point is the opposite — the verifier and allocator are kept SEPARATE specifically so a shared bug is impossible). Register-pressure reporting is a read-only query over already-built intervals (drives the future workbench panel — no workbench exists yet in this project, so this slice's job is just producing the data, not visualizing it).

**8e — Integration Tests & Benchmark** (CHECKLIST bullets 19-24: 3-values/16-registers no-spill test, 40-simultaneously-live/16-registers-with-spills test, verifier-catches-broken-allocation test, libm-call-spills-caller-saved test, coalescing-eliminates-redundant-mov test, 🟡 1000-values-under-50µs benchmark)
These bullets are explicitly cross-cutting integration tests spanning the whole allocator (liveness + intervals + linear scan + spilling + verification all working together on realistic input), unlike 8a-8d's unit-level tests of their own individual pieces — mirroring why Phase 7 kept some integration concerns (the four libm call-sequence tests) separate from selection-level unit tests rather than folding them into 7a-7e. This slice wires the whole pipeline together end-to-end for the first time and is where `SelectedFunction::coalescing_hints` gets consumed for real (the libm-call test also exercises `prologue::SYSV_CALLEE_SAVED`-style caller-saved-vs-callee-saved distinctions, though the REAL byte-level spill-around-a-call sequence is still the deferred final-emission task's job — this slice tests that the ALLOCATOR correctly identifies which values need spilling around a call, not that real spill/restore bytes get emitted).

## Deliberately NOT decided here (deferred to each slice's own design doc)

- 8a: whether `RegClass`/ABI constants live in `forge-regalloc` or a shared location; the exact liveness dataflow algorithm (standard backward per-block iteration to fixpoint is the obvious default, but block granularity vs instruction granularity, and how loop-back-edge interval extension interacts with the fact that this project's IR currently has no loops at all — CHECKLIST.md's own bullet 4 wording ("for values live around a back-edge") already anticipates loops as a stretch goal not yet built, mirroring `Phi`'s own critical-edge caveat from Phase 7a).
- 8b: single class-parameterized `LinearScan` vs two independent instantiations; exact hint-lookup order when both a coalescing hint AND a fixed-register requirement exist for the same interval.
- 8c: spill-slot size/alignment (8 bytes uniformly, per this language's f64-centric type system, is the likely answer but not decided here); whether a spilled value that's reloaded gets a NEW interval (re-entering the active competition) or is handled some other way.
- 8d: the exact shape of the register-pressure report's public API (no workbench exists yet to consume it, so this is speculative until a concrete consumer exists — YAGNI applies; build the minimum CHECKLIST's bullet actually asks for).
- 8e: whether these tests live in `forge-regalloc`'s own test suite or as a new integration-test crate/directory; exact input `Function`/`SelectedFunction` fixtures for the 40-simultaneously-live-values test.

## Exit criteria for this decomposition doc

1. All 24 CHECKLIST.md Phase 8 bullets are covered by exactly one of 8a-8e (no bullet orphaned, no bullet double-covered).
2. Each slice's boundary is a real, testable unit producible without the others already being fully done (8a produces `Vec<Interval>` independent of any allocation logic; 8b assumes unlimited registers and produces a best-effort assignment; 8c adds spilling to 8b's assignment when registers run out; 8d verifies/reports on 8b+8c's combined output; 8e integration-tests the whole thing).
3. `forge-regalloc`'s dependency additions (`forge-ir`, `forge-x64`) are called out as 8a's Cargo.toml responsibility, not left implicit.
4. Consistent with this project's established Phase 7/8 circular-dependency resolution: nothing in 8a-8e emits real machine code bytes; that stays the deferred final-emission task's job.

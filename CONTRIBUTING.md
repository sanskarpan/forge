# Contributing to forge

Thanks for helping improve Forge. The project values small, reviewable
changes, explicit semantics, and reproducible evidence over clever patches.

## Development setup

Forge is developed on macOS and validated across Linux, Windows, ARM64, WASM,
and the Workbench. On Apple Silicon, Docker or Podman can run the Linux ARM64
correctness image without requiring a local cross toolchain.

```sh
git clone https://github.com/sanskarpan/forge.git
cd forge
cargo test --workspace --offline --locked
cargo clippy --workspace --all-targets --offline --locked -- -D warnings
cargo fmt --all -- --check
npm ci --prefix workbench
npm test --prefix workbench
npm run build --prefix workbench
```

Use `make` for the focused targets described by `make help`-style inspection
of the [Makefile](Makefile). Do not run executable-memory or native JIT tests
against untrusted input. Read [SECURITY.md](SECURITY.md) before changing an
unsafe boundary.

## Change shape

1. Open or identify a GitHub issue that states the behavior and acceptance
   evidence.
2. Branch from `codex/integration` with a focused name.
3. Keep each commit to one file. This repository intentionally uses a
   one-file-per-commit strategy so each change can be reviewed and reverted
   independently.
4. Add or update tests in the same change as the behavior they protect.
5. Update `SPEC.md`, `CHECKLIST.md`, or the relevant guide when behavior or
   scope changes.
6. Run the narrowest relevant tests locally, then the full workspace gates.
7. Open a feature pull request into `codex/integration`, link the issue with
   `Closes #N`, and wait for the required matrix.
8. Promote the tested integration branch to `main` with a separate pull
   request and promotion issue. Do not delete `codex/integration` after merge.

The normal GitHub CLI flow is:

```sh
gh issue create --title "..." --body "..."
git switch -c codex/<topic> origin/codex/integration
git push -u origin codex/<topic>
gh pr create --base codex/integration --head codex/<topic> --fill
gh pr checks --watch
gh pr merge --merge --delete-branch=false
```

## Compiler-specific review rules

- The interpreter is the semantic oracle. Compare native results by bits when
  the target is executable, including IEEE edge cases.
- Every encoder change needs an iced-x86 or Capstone round-trip test as
  appropriate for the target.
- IR and allocation verification must remain independent of the code that
  produces the allocation.
- Never introduce an RWX mapping or embed a process-local address in a
  portable artifact.
- External calls must document their exact scalar signature and platform ABI.
- Unsupported operations should return a clear error or use the documented
  interpreter fallback; they must not silently produce approximate results.

## Pull requests

Describe the user-visible behavior, implementation boundary, tests run, and
any platform-specific evidence. If the change touches generated bytes,
include the disassembly or golden-byte result. If a test is intentionally
ignored because it needs codesigning, QEMU, Valgrind, or a privileged host,
state that explicitly and point to the CI lane that covers it.
